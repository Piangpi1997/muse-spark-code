# M50 certification — MCP servers on the Model API backend (PLAN.md M50, D42)

Recorded 2026-09-25. Reconciled onto merged M46 main on 2026-09-26;
certification remains pending a full quality gate after M47–M49 join it.

Before M50 the Model API backend had its own tools and nothing else: the MCP
servers in Muse Code's settings ran only when Muse Code did, and the
extension's own diagnostics tool reached Muse Code sessions only. Now the
window runs those servers itself for the key backend, with an MCP client of
its own (no new dependency), and offers `getDiagnostics` in process.

## What it is built from

No live capture: nothing on the wire is Muse Code's (the client speaks to
the user's servers), and there is no Model API key on this machine. The
shapes come from the specifications and from Muse Code as published:

| Source                                                                         | What it gave                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The MCP specification, revision 2025-06-18                                     | JSON-RPC 2.0 messages, the handshake, `tools/list` pages, `tools/call` results and content blocks, `notifications/cancelled`, the stdio framing, streamable HTTP (POST, JSON or event stream, `Mcp-Session-Id`, `MCP-Protocol-Version`, 202, 404 expiry, DELETE)          |
| Muse Code's docs (extending) and 1.2.1 changelog                               | The settings keys, `required`/`optional`, `${VAR}`, read-only tools run without a prompt under on-request approvals, `startup_timeout_sec`, `tool_timeout_sec`, `cwd`, protocol 2025-06-18                                                                                |
| Muse Code's 1.3.0 binary (read-only scan)                                      | `McpTransportSetting` (`stdio`, `streamable_http`), `McpStdioFramingSetting` (`auto`, `content_length`, `line_delimited_json`: "Probe line-delimited JSON, then fall back to Content-Length framing"), the validation messages, the migrate skill's environment allowlist |
| Meta's Model API docs (tool-calling, structured-output, the Responses schemas) | Function names `[A-Za-z0-9_.-]` with at most one dot; the schema limits; a function's output may be content parts with `input_image`                                                                                                                                      |

## What the model and the user see

- **Tools**: each connected server's tools as `mcp__<server>__<tool>`, so the
  row reads "tool (server)" (M43), with their schemas fitted to Meta's
  limits; `mcp__ide__getDiagnostics` always, as a read.
- **Approvals** (D42's table): Manual and Auto ask, Auto runs a read-only
  tool, Plan refuses all but read-only tools, which ask, Bypass runs; the
  card is a tool's, and "always allow" is kept per tool.
- **Results**: text, pictures as `input_image` parts once checked, the rest
  described; a tool error is a failed row.
- **Loud**: a server that is not running is a warning in the panel once per
  conversation; a required one stops the message with the reason and the
  fix; a settings fault that loads none says which. **MCP servers…** shows
  each server's live state on this backend.

## Windows job-contained stdio launcher, 2026-09-26

The M47-base Windows path now uses the compiled M27 C# assembly for MCP
servers too. A hidden helper opens an actual handle to the creating Node
process, then sends a nonce-bearing READY over a separate local named pipe.
Only that Node process can send GO. The helper checks its bound process
handle, duplicates only the three inherited binary stdio handles, creates
the configured executable suspended, assigns it to a fresh no-breakaway,
kill-on-close Job Object, checks the parent handle again, and resumes the
server. It waits for either the server or its owner to exit; closing the
job then ends descendants, including a grandchild whose launcher already
exited. A missing assembly, failed handshake or failed assignment starts
no server. The server receives only the allowlisted/configured environment;
the private payload, control pipe and nonce are excluded. The Win32 design
follows Microsoft’s [job assignment](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject),
[pipe inheritance](https://learn.microsoft.com/en-us/windows/win32/ipc/pipe-handle-inheritance)
and [kill-on-close](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)
contracts.
