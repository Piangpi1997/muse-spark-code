## Wire and scope

- Meta's [file handling guide](https://dev.meta.ai/docs/file-handling),
  checked 2026-09-25, shows `input_file` with `filename` and an inline
  `data:application/pdf;base64,...` URL on Responses requests. It specifies
  a 50 MB inline limit, text from the first 100 PDF pages, images from the
  first 50, and 50 image slots per request including PDF page images.
- The pinned Muse Code SDK 1.3.0 `TurnInputPartType` is closed to `text`,
  `image` and `skill`; [issue #48](https://github.com/meta-models/muse-code-sdk/issues/48)
  requests file parts. M54 does not invent an MSP wire shape. PDF attaches
  are refused with a direct reason on the Muse Code backend. No Muse Code
  model attempt was needed to learn this type contract.
- No Model API key was used for a live API capture. The fake Responses
  client is the test boundary for payload shape; a live paid request
  remains an explicit release verification gap.

## Implementation under review

- A PDF selected, pasted or dropped on the Model API backend becomes a
  host-held attachment, checked by header and capped at 32 MB locally (Meta's
  50 MB inline cap is per file). Images and PDFs share the per-message budget
  of 48 million encoded data URL characters. An excess file gets a localized
  refusal. A PDF with an unreadable page tree reserves 50 slots. The composer
  shows its name and a file icon.
- A UTF-8 text file picked from a trusted, indexed workspace path becomes a
  named text part on either backend, up to 1 MiB. Canonical path checks stop
  symlink escapes; excluded files remain path mentions and protected/private
  files are refused. Binary bytes are never silently decoded as text.
- A sent PDF becomes an `input_file` Responses content part. The stored
  session keeps the bytes and the user card keeps the name; history reload
  validates them. Model API `read_file` reads confined PDF and image bytes
  for the model; a separate user content part follows the function outputs.
  Other files continue as path mentions and UTF-8 text reads.
- Each replay request and compaction keeps newest media within Meta's
  50-image/page budget and the local 48-million-character encoded-media cap,
  replacing older media with a named explanation and announcing the omission
  in the panel while preserving the local history. PDFs are not uploaded to
  the Files API.
- A tool round admits `read_file` media only while its combined encoded size
  fits the same cap. An excess read gets a failed tool result before its
  base64 data joins the batch; the model and the transcript receive the
  failure reason.
- File picker checks size before reading; postMessage caps base64 length
  before decoding. No new package or escape hatch was added.

## Findings

Muse Code cannot ingest a PDF part until its MSP protocol adds one. PDF
page trees held in compressed or encrypted objects have unknown count;
the model still receives the PDF but the composer reserves all 50 slots
for that message. The stored Model API conversation contains inline PDF
bytes and may grow accordingly (PRIVACY.md).

## Focused PDF page-count boundary audit

The prior parser took the first `/Count` anywhere inside a `/Type /Pages`
dictionary. A valid 50-page PDF whose custom nested dictionary contained
`/Count 1` before the page tree's own `/Count 50` was reported as one page
(focused red test: expected 50, got 1, exit 1). That could admit an image
beside the PDF even though the PDF alone uses all 50 page-image slots.
Further red cases placed `/Count 1` in a custom array, literal string and
comment; the first narrow fix still reported one page in all three cases
(3 failures, exit 1).

The bounded scanner now reads `/Count` only at the page-tree dictionary's
own depth, outside arrays, strings and comments. The valid PDF fixture
recalculates its cross-reference offsets after the custom field is added.
The attachment test confirms the resulting 50-slot reservation refuses an
extra image; the replay test confirms a newer image displaces the older
50-page PDF with a named explanation. PDF, attachment and replay suites
passed 19/19; host and unit TypeScript checks, targeted ESLint and Prettier
passed. These are local fake checks; the original immutable M54 backup
remains at `refs/codex-backups/m54-pre-main-20260925`.

## Stop and read-file replay audit, 2026-09-26

Two focused red tests found that a tool-read PDF could enter a later user
turn's Model API request after Stop, even when the cancelled turn had not
delivered those bytes to a completed response:

- A response called `read_file`, then `ask_user`. Stop cancelled the pending
  question. The next user request still contained `input_file` (test exit 1).
- A response called `read_file`, then its next Model API response was held.
  Stop interrupted that delivery request. The following user request still
  contained `input_file` (test exit 1).

The tool round now adds path-only text for a read file if the round stops or
fails before completion. A cancelled or failed turn also replaces any
synthetic read-file media messages it already queued with that explanation
before the next turn begins. Direct user attachments and successfully
completed turns are unaffected. Both focused tests pass after the fix;
the nine focused M54 suites passed **531/531**, and `npm run typecheck` passed
all five projects (host, webview, unit, e2e, integration), exit 0. Full
quality, browser and accessibility checks remain open on this exact tree.
